# 온톨로지 층 규약

이 문서는 한 지식 저장소의 온톨로지 층(`docs/ontology/`)에 페이지를 쓰는 법을 정한다. 페이지를 쓰거나 고치는 에이전트와 사람이 읽는다.
용어(페이지, 식별자, 교차 참조, 클래스, 관계, 구조 제약, 낡음)는 이 문서에서 쓰는 뜻 그대로다. 이 문서는 루트 저장소가 복사해 주는 루트 관리 파일이라 손으로 고치지 않는다.

## 온톨로지 층의 파일

온톨로지 층은 원본 문서와 분리된 별도의 층이다. 원본 문서(`docs/` 아래의 계획, 정책·정의, 구현 결과 같은 문서)를 읽어 페이지로 정리하고, 원본 문서는 고치지 않는다. 코드는 원본 문서로 삼지 않고 대조용으로만 본다.

```
docs/ontology/
├── ontology.yaml     # 이 저장소의 이름, 공유 범위, 프로젝트의 의존, 하위 클래스, 규칙 덮어쓰기
├── index.md          # 인덱스. 생성물이라 손으로 고치지 않는다
├── skipped.yaml      # 읽고도 기록할 것이 없던 원본 문서의 목록. 필요할 때 생긴다
└── plan/ policy/ term/ decision/ report/ component/   # 클래스별 페이지. 첫 페이지를 쓸 때 디렉토리가 생긴다
```

- 이 파일들은 이 저장소의 것이고 이 저장소에 커밋한다. 루트 저장소의 최신화는 `ontology.yaml`과 페이지를 고치지 않는다.
- `.onto/`는 복사된 기능이다. 이 저장소의 커밋에 들어가지 않는다. 손으로 고치지 않는다.
- `.claude/skills/onto-*/`는 복사된 에이전트 스킬(`onto-ingest`, `onto-query`, `onto-lint`)이다. `.onto/`와 같이 이 저장소의 커밋에 들어가지 않고 손으로 고치지 않는다. 이 저장소 팀의 스킬(`onto-`로 시작하지 않는 `.claude/skills/<이름>/`)은 팀의 것이라 복사가 건드리지 않는다.
- 프로젝트 지침 파일(`CLAUDE.md`, 없으면 `AGENTS.md`)의 `<!-- onto:begin … -->`과 `<!-- onto:end -->` 사이는 온톨로지 층을 안내하는 블록이다. 인덱스(`docs/ontology/index.md`)를 가리키므로 인덱스를 지우거나 옮기지 않는다. 블록 안은 도구가 고치니 손으로 고치지 않고, 블록 밖은 팀의 지침이라 건드리지 않는다.
- 페이지를 쓰거나 고친 뒤에는 `build`로 인덱스를 다시 만들고 `validate`로 확인한다(아래 "확인").

## 페이지

페이지는 엔티티 하나를 서술하는 마크다운 파일이다. 맨 앞에 `---`로 둘러싼 YAML(frontmatter)이 구조화된 속성이고, 그 뒤가 본문이다.

```markdown
---
class: Decision
title: 결제 데이터베이스로 PostgreSQL을 고른다
description: 결제 원장을 담을 데이터베이스를 정한 결정
aliases: [PostgreSQL 채택, Use PostgreSQL]
date: 2026-03-02
about: component/ledger
derivedFrom:
  - path: docs/adr/0001-use-postgres.md
    hash: "0123456789abcdef0123456789abcdef01234567"
---

# 결제 데이터베이스로 PostgreSQL을 고른다

본문…
```

### 키

쓸 수 있는 키는 아래뿐이다. 다른 키는 정의되지 않은 키라 스크립트 검사가 오류로 잡는다(오타가 조용히 버려지지 않게 한다).

| 키 | 뜻 | 값 |
|---|---|---|
| `class` | 페이지의 클래스. **필수** | 클래스 이름 하나(아래 "클래스") |
| `title` | 제목. **필수**, 비어 있으면 안 된다 | 문자열 하나 |
| `description` | 한 줄 설명 | 문자열 하나 |
| `date` | 날짜(결정한 날, 계획을 세운 날 등) | `YYYY-MM-DD` 하나 |
| `aliases` | 별칭 | 문자열의 목록 |
| `partOf` `dependsOn` `implements` `governs` `supersedes` `about` | 다른 엔티티와의 관계 | 식별자 또는 교차 참조. 여럿이면 목록 |
| `derivedFrom` | 근거가 된 원본 문서 | 항목의 목록(아래 "원본 문서") |

값이 없는 키는 쓰지 않은 것과 같다. 키는 영어 그대로 쓴다.

### 클래스

페이지는 클래스별 디렉토리에 둔다. `class`의 값과 디렉토리가 맞지 않으면 오류다.

| 클래스 | 디렉토리 | 무엇을 서술하나 |
|---|---|---|
| `Component` | `component/` | 프로젝트를 이루는 시스템, 모듈, 서비스 |
| `Plan` | `plan/` | 앞으로 할 일을 정한 것. 스킬이 쓴 계획 문서에서 나온 것도 여기에 속한다 |
| `Policy` | `policy/` | 프로젝트에서 지켜야 하는 규칙이나 제약 |
| `Term` | `term/` | 프로젝트에서 뜻을 정해 둔 용어 |
| `Decision` | `decision/` | 대안 가운데 하나를 고른 결정과 그 이유 |
| `Report` | `report/` | 구현한 결과를 기록한 것 |

`Project`는 페이지 없이 `ontology.yaml`에서 만들어지는 엔티티이고, `Source`는 `derivedFrom`이 가리키는 원본 문서다. 둘 다 페이지의 클래스로 쓸 수 없다.
클래스마다 견본이 이 디렉토리의 `<클래스 디렉토리>.md`(`component.md`, `plan.md`, …)로 있다. 복사해서 채운다.

## 식별자

식별자는 엔티티를 가리키는 이름이고, 온톨로지 층(`docs/ontology/`) 기준 파일 경로에서 확장자 `.md`를 뺀 것이다. 별도의 `id` 키는 없다.

- `docs/ontology/plan/auth-redesign.md`의 식별자는 `plan/auth-redesign`이다.
- 경로의 각 조각은 영어 소문자, 숫자, 하이픈만 쓴다(`[a-z0-9-]+`). 공백, 한글, 대문자, 밑줄, 점이 든 이름은 오류다. 한국어 이름은 `title`과 `aliases`에 쓴다.
- 파일 확장자는 소문자 `.md`다. `.MD`나 `.markdown`은 페이지로 읽히지 않아 오류다.
- 이 저장소의 `Project` 엔티티의 식별자는 `project`다. `project`라는 이름의 페이지는 만들 수 없다.
- 같은 이름(제목과 별칭, 대소문자와 공백은 무시)을 가진 엔티티가 같은 클래스에 둘이면 같은 대상이 갈라진 것이라 오류다. 새 페이지를 쓰기 전에 이미 있는지 찾는다.

## 관계와 교차 참조

관계는 엔티티 사이의 방향 있는 연결이다. 페이지에는 아래 표의 방향(쓰는 쪽 → 가리키는 쪽)만 쓴다. 정해진 클래스만 쓰고 가리킬 수 있고, 어긋나면 구조 제약 위반이다.

| 관계 | 뜻 | 쓰는 쪽 → 가리키는 쪽 |
|---|---|---|
| `partOf` | A는 B의 일부다 | `Component` → `Component`, `Project` |
| `dependsOn` | A가 동작하려면 B가 필요하다. 직접 의존만 적는다 | `Component`, `Project` → `Component`, `Project` |
| `implements` | 이 구현 결과가 그 계획이나 결정을 실행했다 | `Report` → `Plan`, `Decision` |
| `governs` | 이 정책이 그 대상에 적용된다 | `Policy` → `Project`, `Component` |
| `supersedes` | 새 것이 옛 것을 대체한다 | 같은 클래스끼리 |
| `about` | 이 페이지가 다루는 대상 | `Plan`, `Decision`, `Report`, `Term` → `Project`, `Component` |

- `Project`는 페이지가 없어 자기가 쓰는 관계를 `ontology.yaml`에 적는다(아래 "`ontology.yaml`"). `Project`가 쓰는 관계는 `dependsOn` 하나다. 값의 형식과 검사는 페이지의 관계와 같다.
- 역방향(`hasPart`, `implementedBy`, `governedBy`, `supersededBy`)은 페이지에 쓰지 않는다. 질의할 때 추론으로 생긴다. 쓰면 오류다.
- `partOf`는 추이 관계다. A가 B의 일부이고 B가 C의 일부이면 질의에서 A는 C의 일부다. `dependsOn`은 추이 관계가 아니다. 간접 의존은 질의에서 경로로 구한다.
- 다른 엔티티와의 관계가 들어오는 것도 나가는 것도 없는 페이지는 고아 페이지라 경고한다. 페이지마다 관계를 하나 이상 적는다. `derivedFrom`은 관계로 세지 않는다.

### 참조하는 법

- 같은 저장소의 엔티티는 식별자를 그대로 쓴다: `about: component/ledger`. `Project`는 `project`다.
- 다른 저장소의 엔티티는 `<저장소 이름>:<식별자>`로 쓴다(교차 참조): `dependsOn: billing:component/api`, `about: billing:project`. 저장소 이름은 그 저장소의 `ontology.yaml`의 `name`이다.
- 관계의 값(`ontology.yaml`의 `dependsOn`도 같다)은 식별자나 교차 참조뿐이다. 파일 경로(`../plan/x.md`, `docs/ontology/plan/x`, `projects/billing/…`), `file:` 주소, `https://…` 같은 주소는 오류(`path-reference`)다. 경로는 옮기면 깨지고, 저장소 밖의 경로는 이 저장소만 열었을 때 열리지 않으며, 다른 저장소의 위치를 드러낸다. 식별자의 첫 조각은 클래스 디렉토리(`component/`, `plan/`, …)이거나 값이 `project`여야 하므로, 그 밖으로 시작하는 값(`componet/api` 같은 오타 포함)도 같은 오류다.
- 공유 범위(`scope`)가 더 좁은 저장소의 엔티티는 가리킬 수 없다. 범위는 `private` < `team` < `public`이다. 더 넓은 범위의 저장소는 가리켜도 되고, 같은 범위끼리는 `team`일 때만 같은 팀(같은 `team:<팀 이름>`, 또는 둘 다 이름 없는 `team`)이어야 한다. 가리키는 엔티티가 없어도 참조에 저장소 이름이 드러나므로 오류(`scope-violation`)다. 범위를 알 수 없는 저장소(`scope`를 적지 않았거나 틀렸다, 온톨로지 층이 없다)는 가장 좁은 `private`으로 본다.
- 가리키는 엔티티가 없으면 깨진 참조라 오류(`broken-reference`)다. 다른 저장소를 가리키는 참조는 그 저장소와 합쳐 검사해야 확인된다. 본문의 링크도 대상이 없으면 같은 오류다(아래 "본문의 링크").

### 본문의 링크

본문의 링크는 페이지 기준 상대 경로로 쓴다(`[설계](../../design.md)`, 페이지가 `docs/ontology/component/` 아래에 있을 때 `docs/design.md`). 링크가 이 저장소 밖의 파일을 가리키면 오류(`outside-link`)다.

- 저장소 밖: 절대 경로(`/Users/me/…`, `C:\…`), `file:` 주소, 저장소의 루트 위로 올라가는 `../`.
- `/docs/design.md`처럼 저장소 루트 기준으로 쓴 링크도 오류다. GitHub는 저장소 루트로 읽지만 편집기는 파일 시스템 루트로 읽어 어느 쪽인지 정할 수 없다. 페이지 기준 상대 경로로 쓴다.
- `http`, `https`, `mailto` 주소와 문서 안의 `#조각`은 파일이 아니라 검사하지 않는다.
- 다른 저장소의 엔티티를 본문에서 가리키려면 파일 경로가 아니라 교차 참조로 쓴다: `[결제 API](billing:component/api)`. 본문의 교차 참조도 관계와 같이 공유 범위 검사(`scope-violation`)를 받는다.
- 링크의 대상이 없으면 깨진 참조라 오류(`broken-reference`)다. 본문의 교차 참조는 가리키는 엔티티가 있어야 하고(등록되지 않은 저장소는 `unregistered-repository`), 이 저장소 안의 상대 링크는 가리키는 파일이나 디렉토리가 있어야 한다. 페이지나 원본 문서를 옮기거나 지운 뒤 남은 링크를 이 검사가 찾는다. 이 저장소만 검사할 때는 다른 저장소를 가리키는 교차 참조는 건너뛰고(루트 저장소가 검사한다), 상대 링크는 검사한다.
- 코드 블록(울타리로 둘러싼 것), 인라인 코드, HTML 주석 안의 링크는 검사하지 않는다. 다만 울타리 없이 4칸 들여쓴 코드 블록은 코드로 알아보지 못해, 그 안의 링크도 링크로 본다.
- 페이지 파일을 다른 저장소(저장소 밖)의 파일에 대한 심볼릭 링크로 두지 않는다. 그런 페이지는 읽지 않고 오류(`outside-link`)로 알린다. 가리키는 파일이 없는 깨진 링크도 저장소 밖을 가리키면 같다(링크 파일 자체가 다른 저장소의 위치를 담는다).
- `ontology.yaml`과 넘긴 문서의 목록(`skipped.yaml`)도 저장소 밖의 파일에 대한 심볼릭 링크로 두지 않는다. 읽지 않고 같은 오류(`outside-link`)로 알린다.

공유 범위 검사의 한계: 검사하는 것은 관계의 값, `class`의 값, 정의되지 않은 키와 그 값(중첩된 키-값의 키 포함), 본문 링크의 교차 참조뿐이다. 제목, 별칭, 본문 글(평문)에 더 좁은 범위의 저장소 이름을 적는 것은 검사가 잡지 못하니 쓰지 않는다(설명과 날짜도 같다). 그 글이 팀이 보는 저장소에 남는다.

## 원본 문서와 `derivedFrom`

페이지는 근거가 된 원본 문서를 `derivedFrom`에 기록한다. 주장의 출처를 따라가고, 원본이 바뀌면 그 페이지가 낡았다는 것을 알기 위해서다.

```yaml
derivedFrom:
  - path: docs/design.md
    hash: "0123456789abcdef0123456789abcdef01234567"
```

- 항목은 `path`와 `hash` 둘로 이루어진다. 항목이 하나뿐이어도 목록으로 쓴다.
- `path`는 저장소 루트 기준 원본 문서의 경로다(`docs/design.md`). `/`로 구분하고, `/`로 시작하거나 `.`, `..`이 있으면 안 된다. 저장소 밖을 가리키는 경로(`../…`, 절대 경로, `file:` 주소)는 값의 종류 오류와 별개로 `outside-link` 오류다(`skipped.yaml`의 `path`도 같다). 다른 저장소의 문서는 원본 문서로 삼지 않는다.
- `hash`는 그 문서의 git 해시(40자리 소문자 16진수)다. 문서를 읽은 시점의 내용에서 구하고, **`status`가 보여 주는 현재 해시를 그대로 옮겨 적는다.** 새로 생겼거나 바뀐 원본 문서는 `status`가 해시와 함께 보여 준다. 낡음 판정도 같은 계산을 쓰므로 `status`가 낸 값이어야 쓰자마자 낡음이 되지 않는다.
  - 해시는 git이 `.gitattributes`와 `core.autocrlf` 같은 줄바꿈 변환을 적용해 낸 blob 해시다. 변환을 건너뛰고 구한 값과 다를 수 있으니 직접 계산하지 않는다. `status`를 쓸 수 없을 때만 옵션 없이 `git hash-object <경로>`로 구한다.
  - 저장소의 blob에 CRLF가 이미 들어 있는 문서는 `git rev-parse HEAD:<경로>`처럼 git에서 직접 얻은 해시와 `status`의 값이 다를 수 있다. 어느 쪽이 맞는지 따지지 말고 `status`의 값을 쓴다.
  - 해시는 항상 따옴표로 감싼다(`hash: "0123…"`). 따옴표가 없으면 YAML이 숫자로만 이루어진 해시를 숫자로 읽어 해시가 아닌 값이 된다. 예를 그대로 따르면 같은 문제가 없다.
- 한 페이지에 근거가 여럿이면 항목을 여럿 쓴다.
- 읽었지만 기록할 것이 없는 원본 문서는 `docs/ontology/skipped.yaml`에 같은 모양(`path`, `hash`)의 항목의 목록으로 적는다. 넘긴 문서는 내용이 바뀌기 전까지 새 문서로 나오지 않는다.
- ingest 대상(원본 문서)의 범위는 규칙의 `sources`가 정한다. 기본은 `docs/**/*.md`이고 온톨로지 층(`docs/ontology/`)은 항상 빠진다.
- 원본 문서는 고치지 않는다. 형식을 맞추려고 원본을 손대면 그것을 만든 스킬이나 사람의 문서가 깨진다.

## 언어

- 식별자, 파일 이름, frontmatter 키, 클래스 이름은 영어로 쓴다. 도구가 안정적으로 다루기 위해서다.
- 제목(`title`)과 본문은 원본 문서의 언어(주로 한국어)로 쓴다. 규칙의 `language.body`가 `source`이면 원본을 따르고, `ko` 같은 언어 코드이면 항상 그 언어다.
- `aliases`에는 규칙의 `language.aliases`에 적힌 언어(기본은 한국어와 영어)의 별칭을 둔다. 어느 언어로 찾아도 같은 엔티티에 닿게 하려는 것이다.

## 하위 클래스

공통 클래스에 없는 이 프로젝트 고유의 종류가 필요하면 `ontology.yaml`의 `classes`에 하위 클래스를 선언한다.

```yaml
name: billing
scope: private
classes:
  Invoice:
    subClassOf: Component
  RecurringInvoice:
    subClassOf: Invoice
```

- 클래스 이름은 영어 대문자로 시작하고 영어와 숫자만 쓴다(`Invoice`). 공통 어휘의 용어(`Component`, `title` 등)와 같은 이름은 쓸 수 없다. `No`, `Yes`, `Null`처럼 YAML이 문자열로 읽지 않는 이름은 따옴표로 감싼다.
- `subClassOf`에는 상위 클래스 하나를 쓴다. 공통 클래스(`Component`, `Plan`, `Policy`, `Term`, `Decision`, `Report`)이거나 같은 `classes`에 선언한 다른 클래스다. 상위 클래스를 따라가면 페이지를 갖는 공통 클래스에 닿아야 한다. 순환하면 오류다. `Project`와 `Source` 아래에는 선언할 수 없다.
- 선언한 하위 클래스는 이 저장소의 네임스페이스에 생긴다. 다른 저장소가 같은 이름을 선언해도 겹치지 않는다.
- 페이지에서는 `class: Invoice`로 쓴다. 페이지는 **공통 조상 클래스의 디렉토리**에 둔다. `Invoice`는 `Component` 아래이므로 `component/invoice-2024.md`다. 선언하지 않은 클래스 이름은 오류다.
- 하위 클래스의 엔티티는 상위 클래스의 엔티티이기도 하다. `Component`를 질의하면 `Invoice`도 나오고, `Component`에 허용된 관계를 쓰고 `Component`를 가리키는 자리에 올 수 있다. 인덱스에서는 공통 클래스의 묶음에 들고 하위 클래스의 이름이 항목에 붙는다.

## `ontology.yaml`

| 키 | 뜻 |
|---|---|
| `name` | 이 저장소의 이름. **필수**. 서브모듈 디렉토리 이름과 같아야 한다. 교차 참조가 이 이름으로 이 저장소를 가리킨다 |
| `scope` | 공유 범위. `private`, `team`, `team:<팀 이름>`, `public` 중 하나이고 다른 값은 오류다(대소문자를 구분하고, 팀 이름은 비어 있지 않고 공백과 `:`가 없다). 처음에는 가장 좁은 `private`이다. 적지 않으면 `private`으로 본다. 공유 범위가 더 좁은 저장소의 엔티티는 참조할 수 없고(위 "참조하는 법"), 이름이 다른 팀의 저장소끼리도 참조할 수 없다 |
| `title` `description` `aliases` | 이 프로젝트(`Project` 엔티티)의 제목, 설명, 별칭. 선택 |
| `dependsOn` | 이 프로젝트가 동작하려면 필요한 `Project`나 `Component`. 선택. 값은 페이지의 관계와 같다(식별자 또는 교차 참조, 여럿이면 목록). `Project`가 쓰는 관계는 `dependsOn` 하나다 |
| `classes` | 이 저장소가 선언하는 하위 클래스(위) |
| `rules` | 루트 기본 규칙(`.onto/rules.yaml`) 가운데 이 저장소에서만 바꿀 값. 같은 구조로 바꿀 값만 적는다 |

프로젝트 사이의 의존은 `dependsOn`에 적는다. 직접 의존만 적고, 값의 검사(깨진 참조, 경로 참조, 공유 범위, 구조 제약)는 페이지의 관계와 같다. 문제는 `ontology.yaml`의 것으로 보고된다.

```yaml
name: billing
dependsOn:
  - shop:project          # 다른 저장소의 프로젝트에 의존한다
  - shop:component/api    # 다른 저장소의 컴포넌트에 의존한다
```

`rules`의 키는 루트 기본 규칙(`.onto/rules.yaml`)과 같다. 바꿀 값만 적고, 적지 않은 값은 기본 규칙을 따른다.

```yaml
rules:
  sources:
    include: ["docs/**/*.md", "design/**/*.md"]   # ingest할 원본 문서의 글롭
  checks:
    orphan-page: {enabled: false}                  # 검사 항목을 끄거나 심각도(error, warning)를 바꾼다
```

모르는 키는 오류다. `rules`로 푸시 관문, 식별자 형식(`language.identifier-pattern`), 공유 범위 검사는 바꿀 수 없다. 식별자 형식은 루트 기본 규칙 하나다.

## 확인

페이지를 쓰거나 고친 뒤 이 저장소의 루트에서 복사된 기능으로 확인한다. 아래 명령은 그 저장소의 지식만 다룬다.

| 명령 | 하는 일 |
|---|---|
| `just -f .onto/Justfile build` | 페이지를 그래프로 컴파일하고 인덱스(`docs/ontology/index.md`)를 다시 만든다 |
| `just -f .onto/Justfile validate` | 스크립트 검사. 구조 제약, 참조, 중복, 인덱스 같은 항목을 기계적으로 검사한다. 오류가 있으면 0이 아닌 종료 코드로 끝난다 |
| `just -f .onto/Justfile query '<SPARQL>'` | 추론이 끝난 그래프를 SPARQL로 질의한다 |
| `just -f .onto/Justfile status` | 새로 생겼거나 바뀐 원본 문서의 목록 |

`validate`의 보고는 문제 하나에 한 줄이고, 탭으로 나눈 다섯 칸(심각도, 지식 저장소, 파일, 검사 항목, 설명)이다. 오류는 반드시 고치고, 경고는 참고한다.
이 저장소 안에서는 어느 디렉토리에서 불러도 이 저장소의 루트가 기준이고(하위 디렉토리에서는 `just -f ../.onto/Justfile …`), 보고하는 경로도 이 저장소 기준이다(`docs/ontology/plan/x.md`).
`validate`는 이 저장소만 검사한다. 다른 저장소를 가리키는 교차 참조(`<저장소 이름>:<식별자>`), 공유 범위 위반(`scope-violation`), 저장소 간 중복, 고아 페이지(`orphan-page`: 다른 저장소에서 들어오는 참조는 이 저장소만으로 알 수 없다), 루트의 `onto/`와 `.onto/` 사본의 비교(`outdated-managed-files`)처럼 이 저장소 밖의 사실이 필요한 검사는 건너뛰고 건너뛰었다고 알린다(표준 오류). 그것들은 루트 저장소가 전체를 합쳐 검사한다. 공유 범위 값(`invalid-scope`), 관계의 경로 값(`path-reference`), 저장소 밖 링크(`outside-link`)는 이 저장소만으로 판단할 수 있어 여기서도 검사한다.
`.onto/`가 없는 클론에서는 이 명령을 쓸 수 없다. 그때는 인덱스에서 페이지로 찾아가 파일로 읽는다.

## 쓸 때 지킬 것

- 원본 문서는 고치지 않는다.
- 새 페이지를 쓰기 전에 같은 대상이 이미 있는지 인덱스와 질의로 찾는다.
- 페이지마다 `derivedFrom`과 관계를 적는다.
- 어떤 명령도 커밋하지 않는다. 쓴 페이지는 `git diff`로 검토한 뒤 사람이 커밋한다.
