# onto-ingest

원본 문서를 읽어 지식 저장소의 온톨로지 층에 페이지를 쓴다. **사용자가 요청할 때만** 한다. 쓴 페이지는 사용자가 `git diff`로 검토하고 커밋한다.

## 작업 위치

- 최상위에 `.onto/Justfile`이 있으면 **지식 저장소 안**이다. 이 저장소의 지식만 다룬다. 명령은 `just -f .onto/Justfile <명령>`, 규약 문서는 `.onto/template/conventions.md`다.
- 최상위에 `onto/Justfile`이 있으면 **루트 저장소**다. `projects/` 아래에 붙은 지식 저장소 전체를 다룬다. 명령은 `just onto <명령>`, 규약 문서는 `onto/template/conventions.md`다. `projects/`가 없거나 비어 있으면 붙인 지식 저장소가 없는 것이다. `just repo add <주소>`로 붙인 뒤에 한다고 알린다.
- 아래에서 `<onto>`는 그 명령 접두어(`just onto` 또는 `just -f .onto/Justfile`)이고 `<규약>`은 규약 문서다.
- 둘 다 없으면 복사된 기능이 없는 클론이다. 이 스킬을 쓸 수 없다. `docs/ontology/index.md`에서 페이지로 찾아 읽는다.

## 지킬 것

- **지식 저장소 단위**로 일한다. 한 번에 저장소 하나만 ingest하고 그 저장소 안의 파일만 쓴다. 루트에서 시작했으면 대상 저장소를 정하고(여럿이면 사용자에게 묻는다) `projects/<이름>/` 안에서만 쓴다.
- **원본 문서는 읽기 전용**이다. 오탈자와 형식도 고치지 않는다(만든 사람이나 스킬의 문서가 깨진다). 쓰는 파일은 `docs/ontology/` 아래의 페이지, `skipped.yaml`, 그리고 `ontology.yaml`의 `dependsOn` 키뿐이다. `dependsOn`은 프로젝트 사이의 의존(`Project`가 다른 프로젝트나 컴포넌트에 의존한다)을 적는 키다. `Project`는 페이지가 없어 거기에 적는다. `ontology.yaml`의 다른 키(`name`, `scope`, `rules` 등)는 고치지 않는다.
- **커밋하지 않고 푸시하지 않는다.** 검토와 커밋은 사람이 한다.
- 코드는 원본 문서가 아니다. 문서의 주장을 코드와 대조할 때만 읽는다.

## 절차

1. **대상 확인.** `<onto> status`를 실행한다. 한 줄에 문서 하나이고 탭으로 나눈 다섯 칸이다: 상태(`새 문서`, `바뀐 문서`), 지식 저장소, 원본 문서(저장소 루트 기준 경로), 현재 해시, 설명. 요청이 저장소나 문서를 정했으면 그 안의 줄만 다룬다. "새로 생겼거나 바뀐 원본 문서가 없다"고 나오면 그렇게 알리고 끝낸다.
   - 페이지에 적는 해시는 이 출력의 **현재 해시 칸 값**이다. `git rev-parse HEAD:<경로>`나 `git hash-object --no-filters`로 구한 값은 줄바꿈 변환 때문에 다를 수 있어 쓰자마자 낡음이 된다.
   - 끝낼 조건: 이번에 읽을 문서의 목록(경로와 현재 해시)이 정해졌다.

2. **규약 읽기.** `<규약>`을 읽는다. 페이지 형식, 키, 클래스와 디렉토리, 식별자, 관계, `derivedFrom`, 언어가 있다. 이 스킬은 규약을 되풀이하지 않는다. 규약대로 쓴다. 클래스별 견본은 규약 문서와 같은 디렉토리의 `<클래스 디렉토리>.md`(`plan.md`, `component.md` …)다.
   - 끝낼 조건: 이번에 쓸 클래스의 견본을 열었다.

3. **문서마다 a~f를 한다.**
   - a. **읽기.** 문서 전체를 읽는다. `바뀐 문서`는 설명 칸에 적힌 낡은 페이지도 연다.
   - b. **기존 엔티티 찾기.** 새 페이지를 쓰기 전에 같은 대상이 이미 있는지 찾는다. `docs/ontology/index.md`를 훑고, 문서가 다루는 이름마다(한글, 영어, 약어) 제목과 별칭을 이름으로 거른 질의로 찾는다. 전체 목록을 뽑지 않는다. 대상 저장소의 엔티티로 좁힌다.
     `<onto> query 'SELECT DISTINCT ?e ?t WHERE { ?e onto:repository "<저장소 이름>" . { ?e dcterms:title ?t } UNION { ?e skos:altLabel ?t } FILTER(CONTAINS(LCASE(STR(?t)), "<이름>")) } ORDER BY ?e'`
     `<이름>`은 소문자로 적는다. 이미 있으면 새로 만들지 않고 그 페이지를 고친다. 같은 클래스에 같은 이름이 둘이면 `validate`가 오류로 잡는다.
   - c. **페이지 쓰기.** 대상마다 `docs/ontology/<클래스 디렉토리>/<식별자>.md`를 만들거나 고친다. 페이지마다 관계를 하나 이상 적고 한·영 별칭을 둔다. 다른 저장소의 엔티티는 교차 참조(`<저장소 이름>:<식별자>`)로만 가리키고 파일 경로는 쓰지 않는다. 프로젝트 자체가 다른 프로젝트나 컴포넌트에 의존한다는 내용이면 페이지가 아니라 `ontology.yaml`의 `dependsOn`에 적는다(`<규약>`의 "`ontology.yaml`").
   - d. **근거 기록.** 페이지의 `derivedFrom`에 근거 문서를 항목으로 적는다. `path`는 `status`의 원본 문서 칸, `hash`는 현재 해시 칸이고 따옴표로 감싼다. 근거가 여럿이면 항목을 여럿 적는다.
   - e. **기록할 것이 없는 문서.** 읽었지만 페이지로 정리할 것이 없으면 `docs/ontology/skipped.yaml`에 같은 모양(`path`, `hash`)의 항목으로 적는다. 파일이 없으면 만든다. 넘긴 문서는 내용이 바뀌기 전까지 새 문서로 나오지 않는다.
   - f. **바뀐 문서.** 낡은 페이지를 새 내용에 맞게 고치고 그 페이지의 `derivedFrom` 해시를 현재 해시로 올린다. 새 내용에 옮길 것이 없어도 낡은 페이지의 해시는 올린다(읽고 확인했다는 기록이다). 이 문서는 `skipped.yaml`에 적지 않는다. 넘긴 문서였다면 여전히 정리할 것이 없을 때 그 항목의 `hash`를 현재 해시로 고치고, 정리할 것이 생겼으면 c~d로 페이지를 쓴다(옛 항목은 지우지 않아도 된다).
   - 끝낼 조건: 문서가 현재 해시로 페이지의 `derivedFrom`이나 `skipped.yaml`에 있다.

4. **확인.** `<onto> build`로 컴파일하고 인덱스를 다시 만든다. 인덱스는 생성물이라 손으로 고치지 않는다. `<onto> validate`를 실행해 오류가 0개가 될 때까지 페이지를 고친다. 경고는 읽고 이번에 쓴 페이지 때문인 것을 고친다. 마지막으로 `<onto> status`를 실행한다.
   - 지식 저장소 안의 `validate`는 교차 참조와 공유 범위 검사를 건너뛰고 stderr로 알린다. 다른 저장소를 가리키는 참조를 썼으면 루트 저장소에서 `just onto validate`로 확인해 달라고 알린다.
   - 끝낼 조건: `validate`의 오류가 0개이고, `status`가 이번 대상 문서를 더 이상 보여 주지 않는다.

5. **보고.** 만든 페이지, 고친 페이지, 넘긴 문서, 남은 경고, 판단이 필요해 정리하지 못한 것을 알린다. `git -C <저장소> status`로 바뀐 파일을 보여 주고 사람이 검토하게 한다. 커밋 메시지를 제안한다: `onto(ingest): <무엇을 정리했는지>`(예: `onto(ingest): 결제 설계 문서에서 게이트웨이와 용어 페이지 추가`).

## 개인 지식은 개인 지식 저장소에 둔다

여러 프로젝트를 비교·종합하는 지식과 서로 다른 저장소의 용어가 같다는 사실은 프로젝트 저장소의 페이지에 쓰지 않는다. **개인 지식 저장소**(비공개 지식 저장소)에 둔다. 팀과 공유하는 저장소에 개인적 해석이 섞이지 않게 하기 위해서다.

- 문서를 읽다가 그런 내용을 만나면 페이지로 쓰지 말고 보고에 "개인 지식 저장소에 둘 것"으로 적는다.
- 사용자가 개인 지식 저장소를 정해 주면 그 저장소를 대상으로 새 ingest를 한다. 같은 용어는 그 저장소의 `Term` 페이지를 두고 본문에서 두 저장소의 용어를 교차 참조 링크(`[청구서](billing:term/invoice)`)로 가리킨다.
- 공유 범위가 더 좁은 저장소의 엔티티는 더 넓은 저장소의 페이지에서 가리킬 수 없다(`scope-violation`). 개인 지식 저장소는 프로젝트 저장소를 가리킬 수 있고 반대는 안 된다.
